## Project Overview

- **Project Name**: ISIFIVE DU Calculator
- **Description**: Analyzes a real git repository and a customer requirement, produces an evidence-based technical profile and Requirement Impact Analysis via an LLM, and deterministically computes a Development Unit (DU) class, count, and price from the AI's per-dimension scores. The AI analyzes and scores; the application decides the DU. Before scoring, an Assumption & Clarification Engine resolves as much as possible itself (facts, safe derivations, documented assumptions) and only asks the user a small, prioritized set of questions that would genuinely change the result. Every scoring decision is persisted with the requirement, resolved context, and assumptions that produced it, forming a traceable history.

## Tech Stack

- **Backend**: Node.js 22, TypeScript, Express, `simple-git` (real git clone/read), `@anthropic-ai/sdk` + Zod (structured AI output), `pg` (Postgres, no ORM)
- **Frontend**: React 18 + Vite, plain CSS (ISIFIVE branding: `#61a60e` / `#007481`)
- **Database**: PostgreSQL 16 (repository snapshots + scoring history; raw file excerpts used during scoring stay in-memory only, never persisted)
- **AI Provider**: swappable via the `AIProvider` interface (`backend/src/ai/getAIProvider.ts`). Repository analysis uses the single legacy `AI_PROVIDER` pointer (`anthropic` default, or `openai`/`openrouter`/`local`). Every other AI call (context resolution, scoring) is chosen **per requirement** from the central Model Registry (`backend/src/domain/models.ts`) spanning Anthropic, OpenAI, DeepSeek, Google Gemini, Alibaba Qwen, local Ollama, and OpenRouter (an operator-configured gateway to many more models, see below) - see the "Multi-LLM Model Registry" convention below. Every call is logged with tokens and estimated cost (`backend/src/ai/pricing.ts`, `store/AIUsageStore.ts`), viewable in the frontend's "KI-Kosten" tab
- **Infrastructure**: Docker Compose (Postgres + backend + nginx-served frontend), deployable as-is on Coolify

## Essential Commands

- **Install dependencies**: `cd backend && npm install`, `cd frontend && npm install`
- **Run locally (backend)**: `cd backend && cp env.example .env` (fill in `DATABASE_URL` and the credential for whichever `AI_PROVIDER` you use - `ANTHROPIC_API_KEY` by default), then `npm run dev`
- **Run locally (frontend)**: `cd frontend && npm run dev`
- **Run tests**: `cd backend && npm test`
- **Typecheck**: `npm run typecheck` in either package
- **Build**: `npm run build` in either package
- **Full stack via Docker**: `cp env.example .env` at the repo root, fill in `POSTGRES_PASSWORD` and `ANTHROPIC_API_KEY`, then `docker compose up --build`
- **Deploy**: point Coolify at this repo's `docker-compose.yml`; set `POSTGRES_PASSWORD` and `ANTHROPIC_API_KEY` as environment variables in Coolify's UI (no `.env` file needed there)

## Project-Specific Conventions

- The AI never states a DU number, class, or price - only per-dimension scores (1-5), evidence, confidence, and descriptive text. `backend/src/scoring/duEngine.ts` is the only place DU/class/price are computed, and it is pure and fully unit-tested.
- Every AI-generated `summary`, `rationale`, and `overallAssessment` is bilingual (`{ en, de }`) - written independently in each language, not machine-translated. See `backend/src/domain/schemas.ts` and the `BILINGUAL_RULE` in `backend/src/ai/prompts.ts`.
- Repository content and AI evidence must be attributable: every `RepositoryFinding` carries a `VERIFIED | INFERRED | UNKNOWN` status per `backend/src/domain/types.ts`.
- Domain history (repository snapshots, requirement contexts, scoring results) is persisted in Postgres via `ScoringStore`, including the file excerpts a repository was analyzed with - so an already-analyzed repository can be reused for a new requirement without re-cloning or re-running the AI analysis.
- Backend fails fast on invalid/missing required configuration (`DATABASE_URL`) at startup; AI provider credentials/model are the one exception, checked lazily by `getAIProvider()` on first AI call, since cloning a repository doesn't need one.
- Every AI call is priced and logged to `ai_usage_log` regardless of provider (`ai/usageTracker.ts`). A (provider, model) pair with no known price (e.g. an unlisted OpenRouter model, no `AI_CUSTOM_INPUT_PRICE_PER_MTOK`/`AI_CUSTOM_OUTPUT_PRICE_PER_MTOK` set) is logged with `costUsd: null` - shown as "unknown" in the dashboard, never guessed. Cache economics (`ai/pricing.ts`) are provider-specific, not a shared constant - Anthropic's explicit `cache_control` breakpoints (`AnthropicProvider`) carry a write surcharge and a steep read discount; OpenAI's automatic caching has neither.
- `ai/prompts.ts` builders return `{ system, stableContext, volatile }`, not a single string: `stableContext` (the repository profile + file excerpts, often tens of thousands of tokens) is byte-identical across a clarification round's repeated calls and across a re-score of the same requirement, so `AnthropicProvider` places an explicit 1-hour `cache_control` breakpoint after it.
- "A missing piece of information is not automatically a question." The AI classifies every information gap (FACT/DERIVED/ASSUMPTION/CLARIFICATION_REQUIRED/UNKNOWN_NON_BLOCKING, see `domain/types.ts`); `scoring/clarificationGate.ts` - pure, deterministic, no LLM calls - decides which of those actually become a question (capped per round, and no new question at all once a round ceiling is reached - both numbers come from the run's `QualityLevel`, see below). Assumptions are never presented as facts, always carry a confidence and a basis, and a user can CONFIRM/REJECT/EDIT one at any time (re-score explicitly afterward - editing an assumption does not auto-spend a new AI call).
- **`QualityLevel` (`quick` | `standard` | `thorough`, `domain/qualityLevels.ts`) is a per-run choice, not a fixed setting** - trades thoroughness for turnaround. Chosen once when a requirement is first submitted (`RequirementPanel`'s Qualitätsstufe picker: Grobschätzung/Standardschätzung/Feinschätzung), then fixed on that `RequirementContext` for its whole lifetime - every later clarification round and the final scoring reuse it (`RequirementContext.qualityLevel`/`ScoringResult.qualityLevel`), so a run never drifts between depths partway through. `QUALITY_PROFILES` maps each level to: effort for `resolveRequirementContext`/`assessRequirement` (Anthropic only - repository analysis has no per-run lever, since its file excerpts are fixed before any requirement exists), `maxClarificationsPerRound`/`maxResolutionRounds` for the clarification gate, and a `rationaleGuidance` prompt fragment that asks the model to visibly scale rationale depth, not just internal thinking time. `AIProvider.assessRequirement` merges impact analysis and DU scoring into one AI call regardless of level (splitting them bought no independence, only a second full generation pass) and the repository context budget (`RepositoryContextBuilder.ts`) is likewise level-independent (fixed at analysis time, before a requirement's chosen level exists).
- **Multi-LLM Model Registry (`domain/models.ts`) is a per-run pick, like `QualityLevel`** - fixed on the `RequirementContext`/`ScoringResult` for their whole lifetime once resolved (`RequirementContext.model`/`ScoringResult.model` always store a *concrete* registry id, never the literal `"auto"`). `MODEL_REGISTRY` is the single source of truth for every *curated* model the app can call - id, provider, wire-level `apiModel` string, display metadata, and pricing; nothing outside this file may hard-code a model string. Seven providers are supported, six of them (`openai`/`deepseek`/`google`/`qwen`/`ollama`/`openrouter`) sharing one `OpenAICompatibleProvider` adapter instance each (only baseURL/apiKey differ - see `ai/getAIProvider.ts` `getAIProviderForModel`), plus `AnthropicProvider` for `anthropic`. Each provider's availability depends only on its own credential (`ai/providerAvailability.ts`), fully decoupled from the legacy single-active `AI_PROVIDER` pointer, which still exists only for repository analysis (no per-run model choice there) and for the legacy `local` value (predating the registry - `ollama` is its registry-native equivalent). **OpenRouter is not part of the curated `MODEL_REGISTRY` array** - it's a gateway to hundreds of models, not a fixed catalog, so its entries are built dynamically from the operator-configured `OPENROUTER_MODELS` env var (`buildOpenRouterEntries`) and appended to `MODEL_REGISTRY` at request time (`buildEffectiveRegistry`, exposed via `ai/providerAvailability.ts` `currentModelRegistry()`); every registry-lookup function (`getModelById`, `listAvailableModels`, `isSelectableModel`, `resolveDefaultModel`, `resolveAutoModel`) takes the registry to search as an explicit trailing parameter (defaulting to the static `MODEL_REGISTRY` for tests) rather than hard-coding which list to use, specifically so the API layer can pass the OpenRouter-inclusive registry while `domain/models.ts` itself stays config-free and pure. `POST /api/requirement-context`'s `model` field accepts a concrete registry id (validated, rejected with 400 if unconfigured/unavailable), the literal `"auto"` (resolved via `resolveAutoModel`'s deterministic, non-LLM rule table - see `AUTO_ROUTING_RULES`), or nothing at all (resolved via `resolveDefaultModel`'s separate, simpler fallback chain - "no model given" and "explicitly optimize for me" are different intents, not the same code path). `privacyMode: "local-only"` forces the local Ollama model with no cloud fallback, ever, and is request-scoped only (never persisted - no DB migration needed for it). An explicit manual pick is never silently substituted for a different provider on failure (`resolveModelSelection` in `api/requirementContextService.ts`); only Auto's rule table may fall back. See `README.md`'s "Multi-LLM Model Selection" section for the full provider/model list and extension points.
- **The Einstellungen tab lets an operator override the zero-config default model without a redeploy** (`api/settingsRoutes.ts`, `store/AppSettingsStore.ts`, a plain `app_settings` key/value table) - `defaultModelId()` in `api/requirementContextService.ts` checks the DB-stored override first, then `DEFAULT_LLM_MODEL`, then the built-in fallback chain (`resolveDefaultModel`'s own chain still applies if the configured id later becomes unavailable). Deliberately does not accept `"auto"` as a default override - "default" and "auto" are different mechanisms (see above) and mixing them would make `defaultModelId()` context-dependent in a way its callers don't provide the criteria for. **Never accepts or stores API keys/secrets** - those stay env-var-only; the tab only ever reports `configured: true/false` per provider, never a credential value.
- **Five models are kept strictly separate and must never be conflated** (see the header comment in `domain/types.ts`): **(A) DU Model** (`scoring/duEngine.ts`) - Base DU: scope/complexity/risk of the deliverable, a pure function of the eight dimension scores; **(B) Technology Fit Model** (`domain/technology.ts`, `scoring/technologyFitEngine.ts`) - how well AI-native custom development, classical manual custom development, n8n, and Intrexx each fit *this* requirement's technical shape; **(C) Effort Model** (`scoring/effortEstimator.ts`) - AI-native's own human-hours corridor; **(D) Commercial Model** (`domain/commercial.ts`, `scoring/commercialEngine.ts`) - Commercial DU: Base DU adjusted for effort deviation/direct costs/innovation/risk, NOT a time conversion; **(E) Pricing Model** (`scoring/pricingEngine.ts`) - the commercial price, decoupled from production effort. `scoring/duEngine.ts` `computeDuResult` orchestrates all five into the final `DuResult`, but each is independently computed and independently tested.
- **DU never produces an artificially precise number past the XL ceiling.** A weighted score > 4.1 always yields `duClass: "XXL"` with `developmentUnits: null` (`mapScoreToClass`) - the old exponential extrapolation (producing numbers like 13/14/17/19 DU) implied far more confidence than the model actually has. `determineScoringStatus` still returns `DECOMPOSITION_REQUIRED` for XXL regardless; the AI's `impactAnalysis.suggestedDecomposition` is the intended path forward, not a bigger DU number.
- **AI_NATIVE is our current production method - git-based custom development with coding agents (Claude Code) - and must never be modeled as a neutral/classical baseline while n8n/Intrexx get real capability profiles. CLASSIC_CUSTOM_DEVELOPMENT (classical, unassisted manual coding) is a distinct fourth technology, not a synonym for AI_NATIVE and not hardcoded to be worse.** This was a documented prior failure mode (`ai/prompts.ts` `ANTI_BIAS_RULE` names it explicitly, including the AI_NATIVE/CLASSIC distinction). All four technologies (`domain/technology.ts` `TECHNOLOGY_IDS`) share one `TECHNOLOGY_CAPABILITY_PROFILES` table on the same -1..+1 scale across the same 12 `TechnologyProfileFactor`s, explicitly labeled `CALIBRATION_STATUS = "INITIAL_HYPOTHESIS"` - hypotheses to be recalibrated later against real ISIFIVE outcomes (see `store/ActualEffortStore.ts`), never presented as measured facts. CLASSIC's own hypothesis values are lower than AI_NATIVE's for every factor (coding agents accelerate, never slow down implementation) but with an uneven gap - narrow for inherently human-driven work (algorithm/architecture design), wide for mechanical generation (forms, CRUD, tests) - so CLASSIC can still clearly beat N8N/INTREXX on custom-logic-heavy requirements while losing to AI_NATIVE (and sometimes N8N) on boilerplate-heavy ones.
- **`relativeEffortFactor` (`scoring/technologyFitEngine.ts`) is symmetric - it can land above OR below AI_NATIVE's own 1.0 reference, for any technology, including AI_NATIVE's own advantage cases.** The old `1 - fitScore * 0.7` formula (capped 30%-100%) could only ever make a low-code platform look cheaper, never more expensive - structurally incapable of representing "n8n would take longer than AI-native here." The new formula computes a `rawEffortScore` per technology (weighted capability effect from `TechnologyProfile` × `TECHNOLOGY_CAPABILITY_PROFILES`, adjusted by that technology's own `ExistingAssetLeverage`), normalizes every technology against AI_NATIVE's own raw score, and only then applies a *technical* guardrail clamp (`RELATIVE_EFFORT_FACTOR_GUARDRAIL_MIN/MAX`, 0.2-3.0 - an error-catching bound, explicitly documented as not a claimed real-world limit). A combination (`N8N_INTREXX`) takes the best-of-both capability per factor but then adds `COMBINATION_INTEGRATION_OVERHEAD`/`COMBINATION_OPERATIONAL_OVERHEAD` on top, so it is never automatically better than both individual technologies - only allowed to be. Each row also carries `contributions` (a signed, sorted per-factor explainability breakdown - "why is n8n at 162%?") and a `varianceFlag: "HIGH_VARIANCE_COMPARISON"` when the factor falls outside `[HIGH_VARIANCE_LOWER_THRESHOLD, HIGH_VARIANCE_UPPER_THRESHOLD]` (0.5-2.0) - a "verify the drivers" nudge, not an error, and distinct from the technical guardrail.
- **The AI never states a fit percentage, a relative effort, a Commercial DU, or a price - only `technologyProfile` (12 factors, evidence-grounded), `existingAssetLeverage` (per technology, `null` = UNKNOWN when the repository gives no evidence either way, never assumed 0), `technologyNarratives` (qualitative advantages/disadvantages), `directCosts`, `implementationNovelty`, and `reusableInnovationIp`.** The actual `relativeEffortFactor`/Commercial DU numbers are always computed deterministically by `technologyFitEngine.ts`/`commercialEngine.ts`, matching the DU Model's own philosophy ("the AI analyzes and scores; the application decides the number") - reproducible and auditable rather than a free-form AI judgment.
- **AI-native effort is a corridor (`minHours`/`likelyHours`/`maxHours`), never a single falsely precise number, and is completely independent of DU** (`domain/schemas.ts` `EffortEstimateSchema`, prompted via `ai/prompts.ts` `EFFORT_ESTIMATE_RULE`) - counts only human time (analysis, briefing/steering coding agents, review, corrections, testing, deployment), never "the AI works for N hours." The old prompting-hours/development-hours split derived from the `aiComplexity` dimension score was removed - a high `aiComplexity` score does not necessarily mean more prompting time (it can come from RAG, tool calling, evaluation, agent architecture, guardrails, ...), so that derivation was not defensible. Every other technology's `estimatedHours` corridor in `technologyComparison` is scaled from AI_NATIVE's own corridor by its `relativeEffortFactor` - never independently estimated by the AI.
- **Commercial DU (`domain/commercial.ts`, `scoring/commercialEngine.ts`) is Base DU adjusted for effort deviation, direct one-time development costs, implementation novelty, and a graduated risk reserve - explicitly NOT `hours / constant`.** "1 DU = 6 hours" no longer exists as a modeling concept anywhere - it was replaced with per-Base-DU-class `EffortBenchmarkEntry`s (`domain/commercial.ts` `BASE_DU_EFFORT_BENCHMARKS`, one per XS/S/M/L/XL, each with its own `expectedLikelyHours`, `calibrationStatus`, `sampleSize`), explicitly NOT a Development Unit definition - just a provisional comparison point for judging whether a requirement's effort is unusually high/low for its class. `commercialEngine.ts` never assumes linearity between classes (`CommercialEngineInput.benchmarks` is even overridable per call, so real ISIFIVE data can later replace these with non-linear figures with zero code change). The effort adjustment is deliberately **asymmetric**: effort above benchmark may raise Commercial DU (dampened by `EFFORT_ADJUSTMENT_WEIGHT`, capped at `±MAX_EFFORT_ADJUSTMENT_FRACTION`), but effort below benchmark - an AI-native productivity gain from Claude Code/coding agents/Konturos/reuse/experience - is surfaced transparently (`CommercialCalculation.effortAnalysis.productivityGain`) without automatically lowering Commercial DU (`NEGATIVE_EFFORT_ADJUSTMENT_ENABLED` defaults to `false`). Since every adjustment this engine computes is therefore `>= 0`, **Commercial DU is structurally floored at Base DU** (`Math.max(rawAdjustedDU, baseDU)` before the technical guardrail is even applied) - Commercial DU falling below Base DU without a deliberate future adjustment source is not possible. The risk reserve is graduated by `aiNativeEffort.confidence` into four tiers (`RISK_CONFIDENCE_HIGH/MEDIUM/LOW_THRESHOLD`) rather than one binary cutoff; below the lowest tier it does NOT apply a markup at all - it sets `CommercialCalculation.estimateStatus = "REQUIRES_CLARIFICATION"` instead, since papering over genuine estimation uncertainty with a bigger number is exactly the false confidence the spec forbids. `RECURRING_RUNTIME`-only direct costs never feed this - only `ONE_TIME_DEVELOPMENT`/`BOTH` costs do; recurring costs are a customer-facing "laufende Kosten" disclosure instead (`ManagementReport.tsx`). Every adjustment is always reported (`CommercialCalculation.adjustments`), even at `deltaDU: 0`; guardrail clamping is fully transparent (`commercialDUBeforeGuardrail`/`commercialDUAfterGuardrail`/`guardrailApplied`/`guardrailReason`).
- **Implementation Novelty and Reusable Innovation/IP are two separate AI assessments, not one "innovation" field** (`domain/types.ts` `ImplementationNoveltyAssessment`/`ReusableInnovationAssessment`, superseding the `@deprecated` `InnovationAssessment` from `commercial-du-v1`). `implementationNovelty` ("how much technically new ground must ISIFIVE cover for THIS requirement") is the only one that may adjust Commercial DU (`IMPLEMENTATION_NOVELTY_MEDIUM/HIGH_BONUS_FRACTION`, still `INITIAL_HYPOTHESIS`). `reusableInnovationIp` ("does this create reusable technical substance for future work") is captured, persisted, and displayed **but deliberately produces zero automatic Commercial DU or price adjustment** - `commercialEngine.ts` doesn't even accept it as an input; `duEngine.ts` attaches it directly to `DuResult` instead, since there is no validated commercial rule yet for pricing reusable IP and inventing one would just be a new arbitrary formula.
- **CLASSIC's Capability Profile values happen to be lower than AI_NATIVE's for every factor today, but nothing in the code enforces that ordering** - `technologyFitEngine.ts` exports its pure `rawEffortScore(profile, capability)` specifically so tests (`technologyFitEngine.test.ts` "Test J - CLASSIC symmetry") can prove the formula treats any two `CapabilityProfile`s identically regardless of which technology name they belong to. Recalibrating CLASSIC's values to beat AI_NATIVE on some factor requires only a data change in `domain/technology.ts`, never a code change - "Capability Profiles are hypotheses, not laws."
- **Pricing is fully decoupled from production effort AND from Base DU** (`scoring/pricingEngine.ts` `computePrice`, `PRICING_STRATEGY` env var) - `HOURLY` (default) derives price from AI-native's own `likelyHours * BILLING_RATE_PER_HOUR` (implied rate always exactly equals the configured rate, by construction); `DU_FIXED_PRICE` derives it from **Commercial DU** `* PRICE_PER_DU` (not Base DU - `PricingInput.commercialDU`), a purely commercial calibration figure with **no implied hours-per-DU conversion** - `null` for XXL, since Base DU (and therefore Commercial DU) is `null` there. `HOURS_PER_DU`/`hoursPerDU` are `@deprecated`, kept only so existing deployments' env vars don't break startup - they feed nothing in the new calculation.
- **GREENFIELD mode (no existing repository) reuses the RepositorySnapshot mechanism instead of a parallel "no repo" flow** - `POST /api/repository/greenfield` creates a snapshot with `mode: "GREENFIELD"` and a synthetic profile immediately (no clone, no AI call), so every existing snapshot-keyed code path (RequirementContext, ScoringResult, history) works unchanged. `ai/prompts.ts` `GREENFIELD_MODE_NOTE` is appended to both `buildContextResolutionPrompt`/`buildAssessmentPrompt` when `mode === "GREENFIELD"`, telling the AI to never mark anything VERIFIED/INFERRED from "the repository" and to set every technology's `existingAssetLeverage` to `null` - live-verified: a real greenfield assessment produced `existingAssetLeverage: null` for all four technologies and an empty `impactAnalysis.existing`, with no fabricated repository evidence.
- **`DuResult.calculationModelVersion` (`"commercial-du-v2"`, `"commercial-du-v1"`, `"technology-fit-v2"`, or absent) is the migration signal for a stored assessment's shape**, not a DB column - a row scored before technology-fit-v2 lacks the field entirely (and has the `@deprecated` `timeEstimate`/`alternativeApproaches` fields instead); `"technology-fit-v2"` rows have `effortEstimate`/`technologyComparison` but no Commercial Model fields; `"commercial-du-v1"` added Base DU vs. Commercial DU with a flat 6h/DU effort reference and a single `innovation` field; `"commercial-du-v2"` (current) replaces the flat reference with per-class `EffortBenchmarkEntry`s, an asymmetric effort adjustment, the `implementationNovelty`/`reusableInnovationIp` split, graduated risk tiers, and full guardrail transparency. All version-specific fields are optional on the TS type for exactly this reason; frontend components branch on which set is present rather than assuming any exists (see `ManagementReport.tsx`/`ResultHero.tsx`).
- **DU confidence, effort confidence, technology-fit confidence, and commercial DU confidence are four separate numbers, never conflated.** A high `confidence.overallConfidence` (DU) does not imply a high `effortEstimate.confidence`, neither implies a high `technologyComparison[].fitConfidence`, and none of them imply a high `commercialCalculation.commercialDUConfidence` - each is computed from a different part of the AI's output (or, for the last one, further discounted when a direct cost item is `UNKNOWN`/`ESTIMATE_REQUIRED`) and can legitimately disagree.
- **Calibration data collection exists but nothing reads from it yet** (`store/ActualEffortStore.ts`, `actual_effort_records` table, `POST/GET /api/requirement/:id/actual-effort`) - records `actualHumanHours`/`actualImplementationMethod` per delivered requirement, together with an immutable `predictionSnapshot` (Base/Commercial DU, effort corridor + confidence, the effort benchmark actually used, the effort/risk-reserve adjustment line items, direct costs, `implementationNovelty`/`reusableInnovationIp`, guardrail before/after/applied, price, etc., all copied at the moment the actual is recorded, since a later re-score would otherwise silently overwrite the original prediction in `scoring_results.du_result`), so today's `INITIAL_HYPOTHESIS` capability/commercial/benchmark hypotheses can later be recalibrated against real outcomes. **Effort calibration (predicted vs. actual human hours) has an objective ground truth; Commercial DU calibration does not** - Commercial DU is a business-model choice, not a technical measurement, so the plan is never to "learn the correct Commercial DU" from `actualHumanHours` directly. No self-learning/auto-adjustment reads this table yet either way - that is explicitly out of scope for now.
